## 0. 先读这一节：本文档的边界

**本文档正文不含任何真实账单数字。**

原因很直接：它会进 Git 仓库、可能被推到 GitHub。而「真实账单数据永不进仓库」
是这个项目的第一条铁律——**报表里那些金额本身就是被保护的对象**。

所以本文档只写「怎么做、为什么这么做、踩过哪些坑」。
**数据现状（有多少笔、报表长什么样）在 `<仓库>\.workbuddy\memory\` 的日志里**，
那个目录被 `.gitignore` 排除，永远不会进仓库。

接手时请先读：`docs/DATA-SAFETY.md`（数据保护） → `docs/IMPORT-DESIGN.md`（导入方案）
→ 本文档（全局视角与踩坑）→ `.workbuddy/memory/` 最新日志（数据现状）。

## 1. 项目是什么

个人记账工具。目标：**每月把自己在支付宝、微信、银行卡的账单导进来，看清钱花在哪。**

约束（按优先级）：

1. **完全本地运行，不泄露任何信息。** 没有网络请求，没有云服务，没有第三方上传。
2. **不重复记账、不错记账。** 宁可报错停机，不可静默算错。
3. 用真实账单数据测试，代码推 GitHub——所以**数据必须在写入 Git 之前就被挡住**。

## 3. 架构

三条独立的链路，各管一件事：

```
① 防泄露链路          ② 导入链路                ③ 存储与报表
─────────────       ─────────────           ─────────────
.gitignore          支付宝 / 微信 / 银行 PDF     内存 SQLite
.githooks/pre-commit  → 嗅探编码与表头           → DPAPI 加密落盘
scripts/vault.ps1      → 还原成二维表            → 去重（三层）
BitLocker（见 §9.1）  → 统一成 Txn              → 分类
                       → 去重 / 分类 / 入库       → 报表
```

**关键点：三条链路互不依赖。** 换一个数据源不需要动存储；改存储不需要动闸门。

### 3.1 本地网页控制台（importer\webui.py）

日常入口是根目录的 `MyLedger.cmd` 双击启动，浏览器自动打开 `http://127.0.0.1:<port>/?t=<token>`。

不变的几条底线（设计上写死的，别为了「方便」放宽）：

1. **只绑 127.0.0.1**，不提供绑别的地址的选项——绑局域网等于把账本摊给整个网络。
2. **URI 带一次性随机令牌**，防本机其它进程「猜端口随便打」。
3. **页面完全自包含**：零外部资源（无 CDN / 字体 / 图标库），不联网，离线可用。
4. **zip / PDF 密码只在内存里活一次**：页面填的密码随本次任务用完即丢，
   不进日志、任务结束就从内存清掉。控制台不提供「记住密码」。
5. **不落任何文件**：日志只活在服务进程内存里，关掉窗口就没了。

架构：一个 worker 线程 + 队列，所有会动账本的操作串行执行；
只读查询共用一把锁，任务在跑时返回上一次快照（标 stale），界面不卡。

`importer\monthly.py` 的 `run()` 为此加了三个参数：`passwords`（页面注入密码）、
`interactive`（必须有终端时才算交互式）、`auto_review`（控制台自己处理疑似重复，
不让服务套服务）。**cli 不传这些参数，行为完全不变。**

## 5. 关键设计决策（每条都有理由，别随手改）

### 5.1 按列名匹配，不按列号

支付宝和微信的导出格式每隔一两年改一次。写死「金额在第 6 列」，改版后不会报错，
**只会把金额读到备注列上**——静默的错误比报错危险一个数量级。

所以：按关键词扫出真正的表头行，再按列名别名表反查下标。改版只需往别名表加一个名字。

### 5.2 去重绝不用 AI

「这两笔是不是同一笔」是确定性判断，金额、时间、单号都是精确值。
让概率模型决定删哪条数据，既不可复现也不可解释，出错时连为什么都不知道。

### 5.3 三层去重，只有第一层自动丢

| 层 | 判据 | 处置 |
|---|---|---|
| L1 | 同源 + 同交易单号 | **自动跳过**（重复导入同一文件天然幂等） |
| L2 | 时间(到分)+金额+对方 完全一致，单号不同 | 标记待确认，**不删** |
| L3 | 金额相同 + 时间 ≤5 分钟 + 对方相似 ≥60% | 标记待确认，**不删** |

L2/L3 不自动合并的原因：跨渠道的同一笔支出（支付宝扣款 + 银行流水）
和「同一分钟在同一家店买了两杯咖啡」在数据上**无法区分**。
机器没有资格替你判断，所以把判断权交回给人。

### 5.4 解析到 0 笔必须报错退出

来自真实事故：一份账单导出文件只有说明和表头、没有任何流水，
但文件开头写着「共 N 笔记录」（N 是几十）。不校验的话会安静地写进一个空批次，
你月底看到「本月零支出」还以为自己没花钱。

**宁可失败，也不能静默算错。**

### 5.5 zip 密码用完即忘；代价是后台无法解压

密码只在交互式运行时提示输入一次，用完即丢，不落盘。

**代价**：后台定时运行没法输密码，所以处理不了加密 zip/PDF。
要么自己解压后丢 csv，要么手动双击 `monthly.cmd`。
这是「不记密码」的必然结果，不是缺陷。

代码里`credentials.py`**不提供「保存密码」这个能力**——不给的能力就不会被误用。

### 5.6 账本加密：内存 SQLite + DPAPI，明文不落盘

```
打开：读 ledger.db.enc → DPAPI 解密 → conn.deserialize() → 全程内存
退出：conn.serialize() → DPAPI 加密 → 原子写回
```

- **不是**「加密文件 + 运行时解密到临时文件」——那会在硬盘上留明文副本
- 没有第三方依赖（不用 SQLCipher，不自己写 AES）
- 用户不用额外记一个数据库密码（密钥由 Windows 用户账户派生）

**代价**：重装系统或换 Windows 账户后解不开。兜底是 `raw\` 里的原始账单归档。

### 5.7 自动化用「登录触发」，不用定时任务

流水线是**幂等**的（同一份文件重复导入不会重复记账），所以跑得频繁零副作用。
登录触发比定时触发可靠，笔记本不存在「到点关机就跳过」的问题。
**也不该用 AI agent 跑这条流水线**——几秒钟的本地脚本，启动一个 AI 会话只多耗电。

### 5.8 依赖：原本纯标准库，PDF 那一步破了例

PDF 解密必须有库，绕不过去。引入 **PyMuPDF**（装在隔离 venv 里，不碰系统 Python），
另装 pypdf 作备选。其余部分仍是纯标准库。

`scripts\monthly.cmd` 与后台执行器会**优先使用该 venv 的解释器**，
否则 PDF 导入会报「没有 PDF 库」。

### 5.9 成功 ≠ 程序没抛异常：批次有明确状态

导入是逐笔写入、单行失败不拖垮整份账单。所以「循环跑完」和「全部写入成功」
是两件事 —— 一个 `ok: bool` 表达不了「98 成 2 败」。

```
started ──→ writing ──→ committed ──→ archived
              │
              └──→ partial_failed ──→ writing（补完重试）
              └──→ failed
```

硬约束只有一条但最关键：**`archived` 只能从 `committed` 来**。
部分失败的批次绝不允许归档 —— 源文件一旦被移进 `_done/`，
失败的那几笔就再也不会被重试，报表上永远少这几笔，且全程没有报错。

`ImportOutcome.ok` 现在是由 `status` 派生的属性，不再是独立字段：
两个来源迟早会不一致，而不一致的方向如果恰好是「状态说失败、ok 说成功」，就又漏记了。

### 5.10 后台日志是白名单，不是「程序输出的副本」

`monthly-run.ps1` 不再捕获子进程输出（`& $python ...` 不赋值，让报告留在屏幕上），
日志改由 Python 自己写：`--log-file` + `importer/audit_log.py`，
一行一条 JSON，只有白名单字段（计数、状态、错误码），文件名过脱敏。

理由很直接：日志不像账本那样加密，却往往是 vault 里唯一一份人人可读的
明文副本，还会被云盘同步和备份。而「把标准输出抄进文件」等于
把解析失败的行、dry-run 预览、异常堆栈一并长期保留。

配套：解析失败记录只留 行号 + 字段 + 错误码，绝不留原始单元格值（见 `sources.py` 头部）。

### 5.11 明文库迁移：先校验，再隔离，之后每次提醒

发现 `ledger.db` 时自动迁移，但**不是**「加密写出去就算完」：

```
核对源文件确实是账本（有 txn / batch 表），否则拒绝，一个字都不写
  → 迁移前算指纹（表清单 + 笔数 + 金额合计 + 时间范围 + 最大 id）
  → 写完密文当陌生文件重开一遍，再算一次指纹
  → 对不上：删掉这份密文、明文原样保留、报错（不留半成品备份）
  → 对上了：明文三件套（含 -wal / -shm）移入 vault\_plaintext_quarantine\
```

之后**每次**打开都会检查明文残留并强提醒 —— 安全提示只提醒一次等于没提醒。
隔离是移动不是删除：校验逻辑本身也可能有 bug，删掉的责任留给用户确认后自己承担。
### 5.12 分类优先级：人工 > 平台分类 > 规则 > 原值，且「人工」必须排第一

四个来源都会给分类：平台自带类目、规则表、本地 AI、人工指定。优先级写死如下：

| 场景 | 优先级 | 存在哪 |
|---|---|---|
| 新导入交易 | 人工指定 > 平台分类 > 商户缓存（规则/AI 的历史结论）> 规则 | `merchant_category` 表 + `txn.platform_category` 列 |
| `recompute` / 回填历史 | 人工指定 > 平台分类 > 规则 > 原值 | 同上 |

三条不能动的规矩：

1. **人工指定永远第一，任何路径都不许覆盖它。**
   `_remember()` 里有一道守卫：`decided_by='manual'` 的记录，
   规则和 AI 来写都直接返回。少了这道，用户手工改完分类，
   下次导入同商户时规则一命中就把它悄悄改回去——功能等于没做。
2. **平台分类不进商户缓存。**
   缓存是「商户 → 分类」的一对一映射，而平台分类是**逐笔**的
   （连锁超市既卖日用品也卖盒饭）。写进缓存等于把其中一笔的答案
   固化成这个商户「永远」的分类，另一笔就被误伤了。
   `setcat` 人工指定仍然进缓存 —— 那是人的决定，逐笔差异就该由人逐笔定。
3. **`recompute` 的原值垫底，`apply_manual` 撤销时却要落到「未分类」。**
   看似矛盾，其实各有用意：
   `recompute` 是在全库重算，原值垫底是为了不把「本地 AI 给过的分类」
   洗成未分类；而撤销人工指定是个明确动作，用户必须看到分类真的变回去了，
   否则命令报「已撤销」而界面纹丝不动，看起来就像撤销失败。

**已知的粒度限制**：人工指定是按**商户（交易对方）**匹配的，不是按单笔。
同一个商户要拆成不同分类（比如同一家超市买了吃和用的）现在做不到。
按商户的粒度换来的是「一次指定、以后自动生效」，覆盖绝大多数场景。

**刻意的取舍**：`recompute` **不读** AI 缓存，只按当前规则重算。
否则「改了规则要重跑以修正历史」这条就没意义了（AI 缓存会把规则盖住）。

## 6. 踩过的坑（本节是本文档最有价值的部分）

分两类：环境类（Windows 特有）和逻辑类。每条都是实测撞出来的。

### 6.1 `.ps1` 必须有 UTF-8 BOM，钩子绝对不能有

Windows PowerShell 5.1 读无 BOM 的 `.ps1` 时会按 GBK 解码，中文注释变乱码，
乱码还会吃掉字符串引号，报出完全误导的语法错误。

反过来，`.githooks/pre-commit` 带 BOM 会破坏 shebang，Git 拒绝执行。

### 6.2 钩子的 shebang 用 `#!/bin/sh`，不要 `#!/usr/bin/env bash`

Windows 上 PATH 里的 `bash` 往往是 WSL 转发器。`env bash` 会命中它，
钩子被 WSL 接管后直接失败——**闸门看起来装了，实际一行都没跑**。

Git for Windows 把 `/bin/sh` 可靠映射到自带 `sh.exe`（实为 Bash 5.x）。

### 6.3 钩子里禁用 `head` / `grep` / `sed` / `cat`

Git for Windows 执行钩子时的 PATH 未必含 coreutils，实测 `head` 直接
`command not found`。**报错走 stderr、退出码可能仍是 0，闸门静默失效。**

只用 shell 内置：正则用 `[[ =~ ]]`（正则放变量里），字符串判断用 `case`。

### 6.4 闸门会把自己的源码判成私钥

检测私钥的正则如果写成完整字面量，`pre-commit` 文件自身就包含那段标记词，
于是**它每次都把自己判成私钥，谁也提交不了任何东西**。
更坑的是：在注释里解释这个坑时把标记词原样写出来，会再次触发。

规避：把标记词拆成两段 shell 字符串拼接（`'PRIV''ATE'`），且**不要在注释里复述它**。

### 6.5 `2>&1` + `$ErrorActionPreference='Stop'` 是终止性错误陷阱

native 命令（git / 7z）的 stderr 会被包成 `NativeCommandError` 并**抛出**。
而闸门被拦截时本来就要往 stderr 写东西 → 自检必然崩在半路。

凡是要读 stderr 的 native 调用，临时降级为 `Continue`，跑完再恢复。

### 6.6 银行截图 OCR：引擎能读金额，读不出日期

实测一张手机长截图（宽约 1200px、高约 9400px）：Windows OCR 单图上限本机是 **10000px**，
图没有超限，但读出来 **冒号 0 个、连字符 1 个**——时间列整列没识别出来。

试过的错路（**别再试**）：
- 切片 + 放大：用「含冒号 + 含连字符 + 含小数点」打分，原生 1x 得 35 分，
  2x 切片得 0 分，3x 切片直接失败。**引擎自己会决定缩放，人为放大后一旦超上限
  会被压回去，比不放还糊。**
- 真正有效的修复是**行内按字符间距拼字段**（Windows OCR 对中文按单字返回 Word，
  不拼的话「-38.50」是三格）。

**结论：截图这条路不可靠，银行流水走 PDF。** PDF 里文字是结构化存储的，
抽出来是精确字符 + 精确坐标，零识别误差。

### 6.7 L3 去重整整一层从未生效

`dedup.py` 里引用了 **`row["ts_dt"]`** —— 那个键**从来不存在**，
L3 每次执行都抛 `IndexError`。

而当时所有测试都是绿的，因为：
- fixtures 那两笔在 L2 就 `return` 了，走不到 L3
- 合成 PDF 的 9 笔金额互不相同，也走不到 L3

直到真实数据里出现「金额相同、时间相近」的两笔，整个导入当场崩溃，
症状只有「解析出 N 笔，写入 0 笔」，看不出原因。

**教训：一条分支只要没被专门构造的数据走过，就等于没写。**
现在有 `tests/test_dedup.py` 专门钉住三层。

### 6.8 `serialize()` 拿的是镜像，落盘验证必须重新读磁盘

清理数据时日志显示「已删除 8 笔」、查询也显示改后的笔数，于是报成成功——
**但文件里根本没变**。因为验证查询跑在**同一个连接**上，看到的是内存状态。

**纪律：落盘类操作，验证必须重新打开文件读回来核对。**
（`secure_store.save()` 现在还加了显式 commit 兜底。）

### 6.9 多线程用 sqlite 连接会报线程错误

`ThreadingHTTPServer` 每个请求一个线程，而连接建在主线程。
Python 默认禁止跨线程使用 → 点一次按钮就抛异常。

修法：`check_same_thread=False` **加一把锁**。
只关检查不加锁，等于把「必现报错」变成「偶发数据损坏」，更难查。

### 6.10 从 WAL 库迁移时 `deserialize()` 必然把连接搞坏

WAL 模式库 `serialize()` 出来的镜像头仍标着 WAL，装进内存库后
SQLite 去找不存在的 `-wal` 文件，**每个查询都报 `unable to open database file`**。
阴险之处是 `deserialize()` 本身不报错，错误延迟到第一次查询才出现。

修法：序列化前先 `PRAGMA journal_mode = DELETE`（顺带 checkpoint）。

### 6.11 Bash 命令里提到 `.ps1` 会被安全策略拦下

不只「调 powershell.exe」会被拦——命令文本里**出现 `.ps1` 文件名**
也可能被判定为「从 Bash 调 PowerShell」而整个拒绝。

绕过：把要传给命令的内容（如提交信息）先写进文件，
再让命令只引用那个文件路径。

### 6.12 给 Windows 程序传路径不要用 `/c/...`

作为 argv 传时 MSYS 会自动转成 `C:\...`，但**写进 heredoc / 文件内容时不会转**，
程序会把它解析成 `C:\c\...`，于是文件被写到意想不到的地方。
统一用 `C:/Users/...` 正斜杠形式。

### 6.13 按「值」猜列位置是错的

重推交易方向时，第一版按「值匹配」在原始行里搜方向列，会把
**备注里恰好写着「收入」的格子**当成方向列，导致收入凭空多算。

修法：按来源的已知列下标取，银行来源整类跳过；
**新导入的行显式记下方向列的取值**，以后不必猜。

### 6.14 规则表的顺序就是优先级，宽关键词必须排最后

`提现充值 / 转账还款` 的关键词（充值 / 转账 / 转入 / 转出）太宽，
排在规则表前面会吸走「话费充值」这种**真实消费**。

同理「缴费」会抢走「学费」。**先具体后笼统**。

### 6.15 `batch_id` 用秒级时间戳会撞主键

`batch_id = 秒级时间戳 + 文件 sha 前 6 位`。部分失败之后**马上重跑**，
或者自动化在同一秒里跑两次同一个文件，两次算出来的 id 一模一样，
`INSERT` 撞 `batch` 的主键 —— 整个导入在 `start_batch` 就崩掉，
源文件永远处理不了。

这个坑是在修 ML-006（部分失败不得归档）时被测试抓出来的：
状态机允许重试，id 却不允许。**改「允许重试」时必须回头看 id 生成。**
修法：撞车时加可读的序号后缀（`.2` / `.3`）。

### 6.16 `fetch` 不会因为 4xx / 5xx 抛异常

复核界面原来的写法：

```javascript
try { await fetch(...); } catch (e) {}
idx++;          // 无论成没成都前进
```

`fetch` 只在**网络层**失败时 reject；HTTP 400/403/404/409/500 都会正常
resolve。所以那个 `catch` 基本不会进，而 `idx++` 在 `try` 外面 ——
请求失败了页面照样跳到下一条，用户以为记下了，裁定静默丢失。

**判断成败必须看 `response.ok`**，而且 `idx++` 只能放在确认成功之后。

### 6.17 「查不到」不能当成「查到了空值」

`recompute` 靠 raw 重推收支方向。raw 是 `{}` 的老记录（schema 默认值）
查不到方向值，而原来的代码继续往下走，`parse_direction("")` 返回**中性** ——
跑一次 `recompute --apply`，一批支出就从报表里消失了，全程没有报错。

「空值」和「没有这个字段」是两件事：
微信的中性交易那一格**真的是空的**，那是答案；
查不到字段则是「不知道」，此时**保持原样**才是安全的方向。

### 6.18 提交闸门会把合成测试数据判成真实卡号

闸门扫到测试里编的 16 位假卡号会直接拦截提交（拦截得对，但它不知道
那是假数据）。**别用 16–19 位连续数字当测试数据** —— 换成 10 位左右，
既能验脱敏逻辑，又不会撞银行卡号规则。

另外：`git commit -m` 的消息里带 `\"` 时，PowerShell 双引号字符串会把
它当成字符串结束符，提交信息被截断成多个参数（报 `fatal: Invalid path`）。
**带引号的提交信息统一写进文件再用 `-F`。**
### 6.19 优先级写反 = 这个功能等于没做

加「手工指定分类」时最容易犯的错，是在重算历史数据的那条路径上
把规则排在人工指定前面。后果是：用户手工把某个商户改对，跑一次
`recompute` 又被规则改回去。**命令跑通了、输出也正常、没有任何报错**，
只是用户会反复觉得「我明明改过了」。

这类错单靠手点一遍测不出来（手点时通常不会紧接着跑重算）。
所以必须用构造数据把优先级钉死，见 `tests/test_manual_category.py`。

对应上一条老教训：**一条分支只要没被专门构造的数据走过，就等于没写。**

### 6.20 「撤销」如果结果看不出变化，就等同于撤销失败

撤销人工指定时，第一版沿用 `recompute` 的「原值垫底」逻辑，
于是规则也认不出的商户撤销后**分类纹丝不动**——命令打印「已撤销」，
界面上一模一样。用户唯一的结论只能是「这功能坏了」。

改写为：撤销是明确动作，退回规则判定；规则也认不出就落到「未分类」，
让变化可见。**同一个「保留原值」的策略，用在重算里对、用在撤销里错。**

### 6.21 `.cmd` 里写中文注释会在 codepage 65001 下自毁

双击 `MyLedger.cmd` 第一次跑就崩，症状是 `'�某...' 不是内部或外部命令`——
cmd.exe 读批处理文件按「推进文件指针」的方式逐行执行，而 codepage 65001 下
指针按**字符**推进，UTF-8 的汉字是多字节的，于是行被整行跳过或被拦腰截断，
剩下的半截被当成命令执行。

实测：`@echo off` + `chcp 65001` 下，含中文的 echo 行有概率直接从执行流里消失。

**修法（已固化在 MyLedger.cmd 里）：**
- `.cmd` / `.bat` 文件**必须是纯 ASCII**（注释用英文写在文件头），无 BOM，CRLF
- 所有中文输出交给 Python 打印——Python 走宽字符 API 写控制台，
  不受 cmd 指针 bug 影响（webui 用 `print(..., flush=True)` 防块缓冲）

### ML-011：平台自带分类 + 交易状态

这一轮把账单里两列「平台已经判好」的信息接进来 —— 以前它们被解析了却
从没被读过（`sources.py` 里的 `category_raw` 别名定义了但没人调用，
`txn.status` 存了也没有任何判定读它）。

- **平台分类**：支付宝「交易分类」/ 微信「交易类型」/ 银行「交易类型」。
  优先级插在人工指定之后、关键词规则之前。映射表 `importer/platformmap.py`。
- **交易状态**：支付宝「交易状态」/ 微信「当前状态」。判定为
  `failed`/`refunded`/`pending` 的**支出**压成中性，不再计入总支出；
  记录留在库里可追溯。`unknown` 一律不动方向。
- **新增只读诊断** `classify`（CLI + 网页「分类诊断」页）：摊开每层的实际
  命中，把「还没被映射的类目」「还认不出来的状态值」单列出来。
- 设计细节与三条纪律见 `IMPORT-DESIGN.md` §2b。
- 回归测试 `tests/test_platform_category.py`（12 组，含判定顺序、
  零信息量拒绝、缓存不污染、双向重推）。

**踩到的坑（都写进代码注释了）**：

1. 状态判定顺序必须是 `failed → refunded → ok`。「退款成功」含「成功」
   两字，先匹 ok 会把全额退款算成正常消费 —— 这条数据从任何角度看都正常，
   不会有任何异常暴露它。
2. `recompute` 重推方向时必须传「未经状态处理的基础方向」。传已压过的值，
   状态改回正常时就再也压不回来 —— 看起来像幂等，实际是单向压死。
3. 平台分类不能进 `merchant_category` 缓存（逐笔 vs 一对一，见上）。
4. `platformmap` 不能在模块顶层 `from .categorize import CATEGORIES`
   —— `categorize` 要 import 它，直接写就是循环导入。
5. 银行 PDF 之前一律走无表头的自动识别，白白丢掉「交易名称 / 交易渠道 /
   附言」三列。现在先试表头，认不出来再退回。

**隐私边界没变**：`platform_category` 是新增的正式列，但取值是**有限固定词**
（平台类目名），和已有的「方向列」同一性质 —— 不是自由文本，不会把商户名
或金额捎带出去。`test_raw_minimization.py` / `test_legacy_raw_compat.py`
里关于它的断言已按新事实更新，但守的仍然是同一条：**raw 里不许有它**。

## 10. 操作纪律（接手者必须遵守）

1. **真实账单永不进 Git 仓库。** 仓库里只有代码 + `fixtures/` 里的合成假数据。
   这条不可协商。
2. **不要把真实账单发给任何云端工具**（包括 AI）。需要处理时先脱敏，或只用表头。
3. **落盘类改动，验证必须重新读磁盘。**
4. **不要用 `.ps1` / `.githooks` 之外的方式改闸门逻辑**，改完必须跑一次真实 `git commit` 验证。
5. **规则改了要跑 `recompute`**，否则旧数据不会跟着变，报表还是错的。
6. **删东西之前先备份。** `recompute --apply` 会自动备份密文，其他操作手动做。
7. **`.workbuddy/` 目录不是缓存**，里面是项目记忆，别删。
8. **分类优先级不许随手改。** 人工指定 > 规则，任何路径都不许覆盖人工指定。
   `recompute` 用「原值垫底」，撤销人工指定则落到「未分类」——两处不一样是有意的，
   见 §5.12。改这条必须同步改 `tests/test_manual_category.py`。
9. **要补分类时，别把商户名发给云端 AI。** 商户名就是账单数据本身。
   用 `unmatched` 自己在本机看、用 `setcat` 自己归，或走本地 Ollama。
